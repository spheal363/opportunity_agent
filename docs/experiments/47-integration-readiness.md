# 本番統合の最小方針

**検索経路以外は変えない。** 今回の 20 件は**固定データとして組み込まない。**

## 変更する範囲

| 箇所 | 変更 |
|---|---|
| `backend/tools/search/` | **検索専用モデル経路を Tool として追加**（`openai/gpt-5-search-api` + Chat Completions + `web_search_options`）。Serper/Jina の Tool は残す（照合に使う） |
| `backend/ai/routing.py` | 新しい工程 `DISCOVERY` を追加。`reads_untrusted=True`、tier は固定モデル指定 |
| `backend/agent/loop.py` | 探索段階を差し替える。**希望別に並列 → 不足方向へ追加検索 → 統合 → 根拠確認**。既存の Goal Analysis / Evaluation / Recommendation の構造は触らない |
| `backend/models/opportunity.py` ＋ `backend/schemas/` | **`model_said` / `verified` / `corrections` / `status` を持たせる**（`candidate_ledger` の形）。**Schema 変更なのでユーザーへ共有 → `docs/api.md` 更新 → backend と frontend を同時に修正** |
| `frontend/src/types/` ＋ 候補一覧 | 「確認済み／訂正済み／未確認／矛盾あり」と**受付の区分**を出し分ける |

## 追加検索の終了条件

**モデルが挙げた件数では数えない。** 重複・条件外・矛盾を除いた**有効候補数**で判定する。

    有効候補 = 掲載できる状態（日程・東京都内・希望適合が確認できた）
    希望ごとに有効候補が目標に届かない かつ 前の巡から有効候補が増えた -> もう1巡
    有効候補が増えなかった -> その希望を止め、「今回調べた範囲で確認できなかった」と記録
    上限（巡数・時間・実費）に達したら止め、理由を残す

既知の候補名を次の巡へ渡して重複を避ける。**参考20件のような外部の正解リストは渡さない。**

## 新規ユーザーで同じ処理が動くこと

固定するのは**手順と終了条件だけ**。イベント名・URL・ドメインは一切コードに書かない。
希望・地域・期間は `UserProfile` と run 開始時の window から取る。
