### 何が起きたかの切り分け

**生レスポンスが無いので、終了原因は断定できない。** 言えるのは保存した範囲だけ。

| 事象 | 保存データから言えること | 言えないこと |
|---|---|---|
| #4・#6 ポケモン | `output` に `message` item が 0 件。**アプリが取り出し損ねたのではなく、取り出す対象が無かった** | **なぜ message が無いのか。** `status` も `incomplete_details` も未取得 |
| #2 DTM・作曲（初回） | `message` はあり、本文 952 字が JSON の途中で切れている。`json.loads` が失敗し、**それを「候補 0 件」と集計した**。これは集計側の誤りで確定 | **切断の原因。** out 8,517 / 上限 9,000 と近いが、**上限付近だったことは原因の証明ではない** |
| 全 6 件 | `status` / `incomplete_details` を読まずに集計していた。**完了か未完了かを区別していなかった** | 各件が実際に完了していたのか未完了だったのか |

**再現で成功したことは、過去の失敗原因を特定したことではない。**
同じ送信内容の 1 リクエスト（`repro/C_pokemon_repro.json`）は
`status: "completed"`・`message` あり・候補ありで成功した。
これが示すのは「**この依頼で候補が得られないわけではない**」ことだけで、
#4・#6 がなぜ message を返さなかったかは**未解明**。

したがって #4・#6 は「候補 0 件」ではなく**最終回答を取得できなかった実行**として扱う。
原因は**不明**のままにする。

## 2. 「13 回」の正体

最小再現（`repro/`）で生レスポンスを取った結果:

| 送信 `max_tool_calls` | `web_search_call` の数 | status の内訳 |
|---|---|---|
| 12（1 件だけ探す軽い依頼） | 4 | `completed` 4 |
| 3 | **3** | `completed` 3 |
| 12（本番と同じポケモン依頼） | **13** | **`completed` 12 ＋ `searching` 1** |

**これは再現で確認した事実であり、本番 6 件の内訳ではない。**
本番 6 件は item ごとの `status` を保存していないため、
13 件の内訳が同じ（completed 12 + searching 1）かどうかは**未取得**。
分かっているのは「`web_search_call` という type の item が 13 個あった」ことだけ。

再現で見えた範囲では、処理されたのは 12 件で、13 件目は上限到達時に
`searching` のまま残った実行中の item だった。

OpenAI 公式仕様（Responses / create）:

> `max_tool_calls`: The maximum number of total calls to built-in tools that can be
> **processed** in a response. ... Any further attempts to call a tool by the model
> will be **ignored**.

「処理される数」の上限であり、**モデルが試みた分まで 0 にする指定ではない**。
観測（12 completed + 1 searching）はこの記述と整合する。

### `web_search_call` の件数が表すもの

**検索クエリ数ではない。** 1 つの `web_search_call` が `action.queries` に
複数のクエリを持つ。再現 C では **13 item にクエリ 29 本**が入っていた。

**「13 件だから 13 回分の課金」とは言えない。** OrcaRouter の仕様は
「内蔵ツール呼び出しは 1 回ごとに課金」と書く一方、
`Per-request cost` は「**billed amount is not reproducible client-side**」とし、
per-call 課金は総額に畳み込まれるとしている。
**内訳はクライアント側で分解できない。** ここでは総額だけを事実として扱う。
処理されなかった 13 件目が課金対象かどうかは、仕様に記述が無く**不明**。

## 3. 費用 — 「不明」は誤りだった

前回「Responses API は実費が取れない」と報告したが、**取得経路がある。**

OrcaRouter `Per-request cost` の記述:

> The surface isn't covered. Embeddings, rerank, images, audio and the native
> `/v1/responses` endpoint are billed but not annotated today.
> **`GET /v1/generation` covers them.**

`usage.cost_usd` が出ないのは**仕様どおり**で、`/v1/generation?id=<request id>` が
権威ある決済記録。保存していた request ID で **9/9 件すべて取得できた。**

| 対象 | 実費 |
|---|---|
| 本番 6 リクエスト（発見工程） | **$1.530500** |
| 最小再現 A（max_tool_calls=12） | $0.089958 |
| 最小再現 B（max_tool_calls=3） | $0.073144 |
| 再現 C（ポケモン・成功） | $0.250348 |
| **診断 3 件 合計** | **$0.413450** |

**照合工程の費用は不明のまま。** LLM を 1 回も呼んでいないので LLM 実費は $0 だが、
Serper 検索 7 回・Jina 取得 11 回の課金は計測していない。**$0 の根拠は無い。**

## 5. 次にどちらへ進むか（判断材料）

**直すべき点は API 側ではなくこちらの実装に多い。**

1. `status` と `incomplete_details` を必ず読み、未完了を最終結果として扱わない
2. 生レスポンスを丸ごと保存する
3. JSON 解析失敗を「0 件」と集計しない
4. `max_output_tokens` は reasoning を含む上限。#2 は out 8,517 / 上限 9,000 と
   近い値で切れているが、**これは原因の証明ではない**。余裕を取るのは予防であって
   原因への対処ではない
5. 実費は `/v1/generation` から取る（`usage.cost_usd` は Responses では出ない）

**検索専用モデル経路（`openai/gpt-5-search-api` + Chat Completions）は、
`usage.cost_usd` が応答に直接乗る**（実測済み: $0.035958 / $0.047018）。
未完了の判定と費用取得の両方が素直になる可能性があるが、未検証。
