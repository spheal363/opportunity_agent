## 本文取得をなぜ別の軸にしたか

現行は Page Reader が `SearchProvider.extract()` を呼んでいた。Tavily が
検索と本文取得の両方を持つため、それで足りていた。

**Serper は検索しか持たない。** 返るのは title / link / snippet だけで、
現行の抽出が入力にしている 800〜1500 文字の本文抜粋が無い。
**検索 provider を替えるだけでは、抽出の入力が痩せる。**

`tools/fetch/` を別に切り出し、`PAGE_FETCHER` で選べるようにした。
`SerperProvider.supports_extract` は False のままで、**持つふりをさせない。**

### 実験用に Jina Reader を選んだ理由

| 候補 | 取得成功率 | 速度 | 費用 | 実装負荷 |
| --- | --- | --- | --- | --- |
| **Jina Reader** | 未計測 | 未計測 | **キー無しで動く**（20 RPM）。キー有で 10M トークン無料枠 | 小（GET 1 本） |
| 自前 HTTP＋本文抽出 | 未計測 | 未計測 | 通信費のみ | **大** |
| Tavily Extract | 未計測 | 未計測 | Tavily の従量（**未確認**） | 済（比較の基準線） |

**新規契約も支払いも無しで今日試せる**のが決め手。

自前 HTTP 取得は費用こそ最小だが、**このプロセスから直接取りに行くことに
なり、SSRF が実際のリスクになる。** 現在の URL 判定は名前解決をしておらず、
リダイレクト追跡も無い。そこまで作る時間は Code Freeze までに無い。

### 取得できても確認できたとは限らない

- **申込先にしか期限が無いページがある**（Google Form、Peatix など）。
  全文取得＝期限確認完了とは扱わない。
- **本文はキャッシュのことがある。** Jina 側の取得時刻は制御できない。
  `availability_checked_at` はこちらが確認した時刻であって、ページが
  更新された時刻ではない。
- **切り詰めで募集要項が落ちうる。** 末尾の締切表記が消える可能性がある。
  期限が無いことを終了の根拠にしない。

## Jev について確認したこと

出典は公式（typesafe.ai / docs.typesafe.ai）。

- **文字列を生成しない。** 公式が "gives up string generation" と明記。
  推薦理由のような自由文と、任意の日時抽出は**代替できない**
- primitives は Choice / Score / Noul。質問は 1 リクエストにまとめられ、
  それぞれ独立に並列評価される
- Score は水準の並びを渡し、**確率で重みづけた期待値**が返る。
  0〜(水準数-1)。**異なる分布が同じ値になりうる**
- `confidence` は**分布の尖り具合**。公式が「正解率ではない」と明記
- $0.042 / MTok（入力のみ。出力は無料）
- 応答の `model` に**実際に答えたバージョン**が入る（alias は解決後の値）
- 70ms〜500ms、40〜200 倍速はベンチマークであって保証ではない。
  **このアプリの予測時間として使わない**

### 設計上そこから決めたこと

- **関連性と意外性を別の質問にした。** 1 つに混ぜると多次元の質問になり、
  公式が confidence 低下の原因に挙げている
- Score を既存の 0-100 へ写してから `score + 0.3 × serendipity` に渡す
- **点が返らなかったときに 0 点としない。** 0 は「無関係」という判断で、
  「分からない」ではない
- confidence が閾値未満なら**既存 LLM へ戻す**。その費用は LLM 側の欄に乗る
- `match_reasons` / `concerns` / `evaluation_summary` は **None**。
  空文字や当たり障りのない語で埋めて互換性を装わない
- **型保証は判断の正しさでも Prompt Injection 耐性でもない。**
  外部データは境界を明示して渡すが、それは防御ではない

## 比較の進め方

### ① 固定データで処理方式を比べる

`backend/tests/fixtures/candidates.py`。**検索の抜粋から始める。**
抽出済みの DB 行から始めると、抽出そのものの差が見えない。

取得日時も固定する（`NOW`）。「いま」が動くと受付中か終了かの判定が
日によって変わり、比較にならない。

含めているもの: 締切切れ / 開催終了 / 受付中 / 日時不明 / 重複 /
取得失敗 / 意外だが関連する候補 / 記事。

**ここでネットワークを省いた時間を、実探索全体の時間とは呼ばない。**

### ② 同じプロフィール・同じ検索語で検索サービスを比べる

1. **まず検索語をそろえて** Tavily と Serper の候補を比べる
2. 日本語のイベント・ハッカソン・コミュニティで行う
3. 必要なら後から検索語をサービス別に調整するが、**最初の比較と分ける**

**少数実行の平均だけで速度改善を断定しない。** サンプル数とばらつきを示す。

## 品質の見方

**現行 TOP3 との一致率を品質指標にしない。** 現行が正解ではない。

| 指標 | 見るもの |
| --- | --- |
| 明確な期限切れ・受付終了 | 最終推薦に残った数（**0 が目標**） |
| 受付状況 | `open` を確認できた数 / `unknown` の数 |
| 根拠 | 公式ページで確認できた数（`verified`） |
| 関連性・意外性 | 分布と、意外性枠が機能したか |
| 取りこぼし | **Jev の粗い選別で落とした有望候補** |
| 重複・不足 | 重複の残存数、3 件に満たなかった回数 |
| 人の確認 | 内容を読んだうえでの評価 |

「Jev の粗い選別で落とした有望候補」は、**選別を通さず全件読んだ結果
（構成 A）と突き合わせて数える。** 選別後の結果だけでは測れない。

## 計測

run ごとに `AgentRun.usage_json` へ入る。

- 全体および工程別の経過時間（**並列呼び出しの合計ではない**）
- 検索リクエスト数、本文取得の試行数・成功数
- **Jev と LLM それぞれ**の試行数・トークン・費用
- Retry / Fallback / 使用量不明
- 候補が落ちた理由別の件数、最終結果の受付状況の内訳
- 走った構成（provider / fetcher / pipeline / evaluator / モデルバージョン）

### 費用の扱い

| | 状態 |
| --- | --- |
| LLM（OrcaRouter） | **円は見積もり。** 公開価格から置いた値で、請求額ではない |
| Jev | **公式単価 × 実トークン**（$0.042/MTok、出力無料）。**円に換算しない**（為替を推測で置かない） |
| Tavily | **未確認。** 回数のみ記録 |
| Serper | **未確認。** 無料枠 2,500 クエリは公式。単価は公式ページを取得できていない |
| Jina Reader | **未確認。** キー無しで動く範囲では支払いが発生しない |

**無料枠内で支払いが発生しないことと、使用量がゼロであることは別。**
使用量は常に記録し、支払い条件は別に書く。

| | 見積もり | 根拠 |
| --- | --- | --- |
