# #26-b モデル振り分け

実装は `backend/ai/routing.py`。**方針はそこ 1 か所だけに書く。**

## 判定の要約

| | |
| --- | --- |
| 実装 | 完了（振り分け表・制約のコード化・工程別ログ・戻す手段） |
| 実測した工程 | 検索計画 1 つだけ（STANDARD vs CHEAP、prompt 修正の前後で 2 回・計 24 実リクエスト） |
| 実測の結果 | **不合格。CHEAP を採用しない** |
| 既定 | **全工程 STANDARD のまま**（＝現行維持） |

速度は 3 倍、実費は 14 倍の差があったが、**品質の受け入れ条件を満たさなかった。**
劣化のうち「入力に無い年の補完」は prompt 修正で消えたが、**「目標の軸の欠落」は
残った。** 詳細は下の「検索計画の比較」。

## 何を根拠に「簡単」「難しい」を決めるか

工程名では決めない。次の 4 つで決める。

    入力の出所      Web 本文を読むか。外部由来のデータを読むか
    判断の重さ      事実の抽出・突き合わせか、語句の組み立てか
    呼び出し数      1 run あたり何回呼ぶか（費用と時間に直接効く）
    許容できる時間  直列の待ち時間に乗るか、並列に逃がせるか

呼び出し数と時間は `run_548d4541e6e8`（2026-09-22、構成 C）の実測値。

## 工程別の振り分け

| ② 検索計画 | ①の出力 + 活動地域 | 検索語を 3〜4 個作る | STANDARD | Fallback のみ | 外部本文は読まない。CHEAP を実測したが**不合格**（下記） | 1・14.3・0.84 |

| ⑦ 検証 | **公式ページ本文** | 突き合わせ | STANDARD | Fallback のみ | 外部本文を直接読む。**CHEAP 禁止** | 3・39.2・3.12 |

### 「上位へ移る条件」が Fallback だけである理由

POWERFUL は 1 呼び出し 4.5 秒（#14 実測）。通常経路に置くと探索が止まって見える。
**通常 tier としては 1 工程も使わない。** 上がるのは STANDARD が試行を使い切ったときだけ
（`ai/llm.py` の `_FALLBACK_TIERS`）。デモのために POWERFUL 呼び出しを足さない。

これは表そのものをテストで縛っている（`ai/routing.py` の `_check_table`）。
POWERFUL を通常 tier に書くと import 時に落ちる。

### 外部由来をどこまで広げるか

**「Web 本文そのもの」だけを外部扱いにしない。** 抽出結果の `description` に
指示らしき文が残っていれば、評価も推薦理由もそれを読む。`reads_untrusted` を
付けているのは抽出・評価・推薦理由・検証の 4 つで、この 4 つは CHEAP にできない
（`_check_table` が import 時に落とす）。

目標分析と検索計画は外部本文を読まないが、**プロフィールを信頼するわけではない。**
どちらも `untrusted_block` で囲み、system に `UNTRUSTED_DATA_RULE` を付けたまま。
tier を変えてもこの防御は外さない。

### Memory・外部候補の混入を確認した

- `_analyze_goal` の入力は `UserProfile` の列だけ（`agent/loop.py`）
- `_plan_search` の入力は目標分析の出力と `profile.location` だけ
- `ai/schemas/reflection.py` は定義のみで、**Agent Loop から呼ばれていない**

検索結果・ページ本文がこの 2 工程へ入る経路は無い。

## 検索計画の比較（実測）

### なぜ検索計画を最初に選んだか

CHEAP 化の候補は目標分析と検索計画の 2 つ。検索計画を先にした理由は 3 つ。

1. **効果が大きい。** 費用 ¥0.84 と時間 14.3 秒で、目標分析（¥0.28 / 5.0 秒）の約 3 倍
2. **失敗しても波及が狭い。** 目標分析の出力は検索計画・評価・推薦理由の 3 工程が読む。
   検索計画の出力は検索クエリにしかならない
3. **品質を機械的に見られる。** 出力が enum + 短い文字列で、方向の数・種別の散らばり・
   地名の保持・日本語比率を数えられる

### 条件

    固定入力 3 件（個人情報なし）× 2 設定 × 2 回 = 12 実リクエスト
    Retry なし・Fallback なし（切り分けのため）
    検索・本文取得・全 run はやり直していない
    standard  google/gemini-2.5-flash
    cheap     openai/gpt-4o-mini

再現: `backend/.venv/bin/python -m scripts.compare_search_plan_tier --confirm`
生データ: `docs/experiments/26-search-plan-tier.json`（1 回目・prompt 修正前）

**以下は 1 回目の結果。** prompt を直した 2 回目は後の節にある。

### 数字

| | 実費 USD | 中央値 | reasoning tokens | Schema 通過 |
| --- | --- | --- | --- | --- |
| standard | 0.022658 | 7,505 ms | 6,918 | 6/6 |
| cheap | 0.001594 | 2,449 ms | 0 | 6/6 |

**実費は 12 件すべてで取得できた**（`ORCAROUTER_INCLUDE_COST` を有効にして実行）。
見積もりではなく OrcaRouter が返した値。差は費用 14.2 倍・時間 3.1 倍。

機械判定（方向数・serendipity の有無・地名の保持・日本語比率・記事語の混入）は
**両者とも 6/6 で同点。**

### それでも不合格にした理由

**一致率と機械判定だけで判定しない。** 出力を読むと、CHEAP に 2 種類の劣化があった。

| 劣化 | 発生 | 内容 |
| --- | --- | --- |
| 目標の欠落 | cheap 1/2 | `jp_engineer` は目標の軸が「AIプロダクト開発」と「起業」の 2 つ。cheap #1 は起業に当たる方向を 1 つも作らなかった。standard は 2/2 で両方を覆った |
| 根拠のない補完 | cheap 1/2 | `open source hackathon Berlin **2024**`。入力に年は無い。**今日は 2026-09-22 で、過去の年を検索語に入れている** |

方向の数も、`jp_engineer` では cheap が 2/2 とも 3 個、standard は 4 個だった。
規則の範囲内（3〜4）だが、prefilter が読む 8 件をより少ない方向で埋めることになる。

**どちらも入力に対する忠実さの問題で、速度・費用では埋め合わせられない。**
「目標・制約の保持」と「根拠のない補完をしない」は比較を始める前に置いた条件で、
後から基準を下げない。

## prompt を直して測り直した（2 回目）

1 回目の劣化は prompt に規則が無かったせいかもしれない、という仮説で
`ai/prompts/search_plan.py` に 2 つの規則を足し、**同じ条件でもう 12 リクエスト**
測り直した。生データ: `docs/experiments/26-search-plan-tier-v2.json`。

    規則 2  「探索の軸」はどれも最低 1 つの方向で覆う（例つき）
    規則 4   入力に書かれていない年・月・日付を query に入れない

判定を目視に頼らないよう、検査も 2 つ足した（`covers_all_goals` /
`no_invented_year`）。**足した検査を旧データにかけ直し、1 回目に目視で見つけた
2 件をちょうど捕まえ、他を誤検知しないことを先に確かめている。**

### 結果

| 検査 | standard 旧→新 | cheap 旧→新 |
| --- | --- | --- |
| 軸をどれも覆う | 6/6 → 6/6 | 5/6 → **4/6** |
| 入力に無い年を入れない | 6/6 → 6/6 | 5/6 → **6/6** |
| Schema 通過 | 6/6 → 6/6 | 6/6 → 6/6 |

**片方だけ直った。**

- **年の補完は消えた。** 規則 4 は効いた
- **軸の欠落は残った。** 規則 2 は例まで書いたのに、cheap は `jp_engineer` で
  2/2 とも「起業」に当たる方向を作らなかった（1 回目は 1/2）。方向も 3 個止まりで、
  4 個目を作る余地があるのに使わない

```
cheap  AIプロダクト ハッカソン 東京 募集 / AI 教育 勉強会 東京 参加者募集 / AI 音楽 コンペティション 募集
       -> 「起業」が 1 つも無い

standard  AI プロダクト開発 ハッカソン 東京 募集 / 起業支援 プログラム 東京 参加者募集 / ...
       -> accelerator の方向で軸を覆っている
```

n=2 の小さい標本なので「4/6 は 5/6 より悪い」とは言えない。言えるのは
**規則を足しても cheap の軸の欠落は無くならなかった**ということ。

### prompt 修正そのものの費用

規則を足したぶん入力トークンが増える。**これは確定値**（実費も取得済み）。

| | 入力 token | 実費 USD（6 件） |
| --- | --- | --- |
| standard 旧 → 新 | 711 → 886（+175） | 0.022658 → 0.023784（**+5.0%**） |
| cheap 旧 → 新 | 884 → 1100（+216） | 0.001594 → 0.001688（+5.9%） |

所要時間は中央値が動いた（standard 7,505 → 8,344 ms）が、**範囲が重なっており
差とは言えない**（旧 5,410〜10,208 / 新 6,612〜11,068、各 6 件）。

**実際に使っているのは standard で、standard は元から 2 つとも 6/6 だった。**
つまりこの prompt 修正は、いま動いている経路にとっては **+5% の費用増で、
測定できた品質の向上は無い**。1 run あたりでは ¥0.84 → ¥0.88 程度（run 全体の 0.3%）。

規則 4（年を入れない）はモデルに依らない誤りの予防なので残す価値がある。
規則 2（軸を覆う）は**目的を果たせていない**うえにトークンの大半を占める。
外すなら測り直しが要るので、今回は両方を残したままにしてある。

### 判定

**CHEAP は採用しない。検索計画は STANDARD のまま。**

「目標・制約の保持」は比較を始める前に置いた条件で、prompt を直しても満たせなかった。
速度 3 倍・費用 14 倍の差があっても、後から基準を下げない。

**「CHEAP では駄目」と言い切るには標本が足りない**（各 6 件）。
言えるのは「規則を足した prompt でも、CHEAP へ替える根拠は得られなかった」まで。

## 元へ戻す

振り分けを入れる前の挙動へは環境変数 1 つで戻る。

```bash
LLM_ROUTING=standard
```

表を無視して全工程 STANDARD になる。`llm.routed` の `why=` が
`LLM_ROUTING=standard のため振り分けを使わない` に変わるので、ログで区別できる。

**現在の既定（`LLM_ROUTING=policy`）でも全工程 STANDARD なので、実際の tier は同じ。**
違うのは、方針と理由が表とログに出るかどうか。

## #54 のデモで見せるもの

### 実行とログの取り方

```bash
cd backend && .venv/bin/uvicorn main:app --reload --port 8000 2>&1 | tee /tmp/demo.log
```

画面（`http://localhost:5173/app`）から探索を 1 回走らせ、終わったら工程ごとの
判断だけを取り出す。

```bash
grep llm.routed /tmp/demo.log
```

1 論理呼び出しにつき 1 行出る。

```
llm.routed step=extraction requested=standard why=Web 本文をそのまま読む。8回/run で費用の過半を占める
           model=google/gemini-2.5-flash attempts=1 fallbacks=0 tokens=600 reasoning=95 usd=0.000360 result=ok
```

**`requested` と `model` を別々に出している。** これが無いと、振り分けでそのモデルに
なったのか、Fallback で上がったのかを後から言い分けられない。

### 1 run の構成と参考費用

| | |
| --- | --- |
| 構成 | 既定のまま（Serper + Jina + Jev + prefilter、`LLM_ROUTING=policy`） |

### 正直に言うべきこと

- **POWERFUL は発動しない見込み。** 通常 tier に置いていないので、
  モデル障害が起きない限り 0 回。ログに出なければ「発動なし」と言う
- **全工程 STANDARD のまま。** 「安い AI を使っている」ことは今回の実測では示せない。
  示せるのは「工程ごとに方針と理由を持ち、外部データを読む工程には安いモデルを
  使わないと決めてある」ことと、その判断がログに 1 行ずつ残ること
- 障害を模擬した Fallback のデモを見せる場合は、**通常実行の実測と分けて**説明する
